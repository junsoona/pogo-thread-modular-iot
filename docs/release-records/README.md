# 설치·실물 시험 기록

빌드 manifest는 "이 파일들이 어떤 빌드인가"만 말한다. **어디에 넣었고 무엇을 확인했는가**는 여기에
따로 기록한다(`docs/versioning.md`). 기록이 없는 설치는 이 저장소 기준으로 "알 수 없음"이다.

## 파일

| 파일 | 내용 |
|---|---|
| `YYYY-MM-DD-<대상 별칭>-<짧은 설명>.md` | 공개 기록. 저장소에 커밋한다 |
| `private/…` 또는 저장소 밖 | 비공개 기록. **커밋하지 않는다**(`.gitignore`가 `private/`를 무시한다) |
| `legacy-artifacts.md` | 버전 체계 이전 산출물의 목록 (명시 버전 미관리) |

빈 양식은 도구가 만든다. 저장소 밖에 만든 뒤 공개 부분만 이 디렉터리로 옮긴다.

```bash
tools/pogo_version.py record-template --out <저장소 밖 디렉터리>
# install-record.public.md, install-record.private.md
```

## 공개 기록에 적는 것

1. **일시**(시간대 포함)와 기록자.
2. **대상 별칭.** 예: `bench-base-1`, `home-hub`. 별칭이 실제로 무엇인지는 비공개 기록에만 있다.
3. **설치한 조합.** 구성요소(앱, `power_base`, `module`, `rcp`, `linux_bridge`)마다:
   - 버전, 빌드 식별자, 빌드 종류
   - `manifest.json`의 SHA-256과 주 산출물(앱 이미지, 실행 파일, 앱 번들 manifest)의 SHA-256
   - 이번에 바꾸지 않은 구성요소는 "변경 없음"과 이미 들어 있던 빌드. 모르면
     "알 수 없음 (이 체계로 관리되지 않음)". **추정해서 적지 않는다.**
4. **시험한 단계와 결과**(통과 / 실패 / 하지 않음)와 근거 로그·화면의 파일 이름.
5. **검증하지 않은 범위.** 비워 두지 않는다.
6. **되돌릴 산출물.** 구성요소마다 직전 산출물의 SHA-256과 보관 위치.

설치 전에 `tools/pogo_version.py manifest-verify --dir <artifact>`가 통과한 산출물만 기록한다.
배포 후보를 설치하는 것이면 `--release`로 확인한다.

## 공개 기록에 적지 않는 것

- 보드 EUI-64·일련번호, 직렬 포트 이름, 호스트 이름, IP·Thread 주소, 계정 이름, hub_id
- 설정 이미지(`*_cfg.bin`), Dataset, 백업 이미지의 **해시**(비공개 기록에는 적어도 된다)
- 설정 코드, PSKd, Thread Dataset, Network Key, 관리 키, 토큰 — **값은 어느 기록에도 적지 않는다.**
  비공개 기록에도 "어디에 보관하는가"만 적는다.

근거 로그를 첨부할 때도 같은 기준으로 가린다(`docs/validation-status.md`의 "기록 원칙").

## 두 저장소에 걸친 조합

앱(`pogo-sensor-ios`)과 이 저장소의 구성요소를 함께 내보냈으면 한 기록의 표에 같이 적는다. 앱 줄에는
저장소 이름, 태그 또는 commit 전체 SHA, 버전과 빌드 번호(`1.0.0 (2)`), 빌드 식별자, 앱 번들
manifest의 SHA-256을 적는다. 앱 저장소의 CHANGELOG는 이 기록의 파일 이름을 가리킨다.
